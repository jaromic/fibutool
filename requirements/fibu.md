# fibutool — Requirements

fibutool processes bank payment receipts and invoices (both as PDFs) and produces a
bookkeeping journal (CSV) and merged PDF archive for Austrian Einnahmen-Ausgaben-Rechnung
(Ist-Besteuerung / cash-basis accounting).

---

## Glossary

| Term | Meaning                                                                     |
|---|-----------------------------------------------------------------------------|
| Payment receipt | A bank booking receipt PDF (one per transaction)                            |
| Invoice document | An invoice or credit note PDF (one file per invoice document)               |
| Booking date | The date money actually moved; drives all journal entries and VAT deadlines |
| Invoice date | The date printed on the invoice; used for matching only                     |
| Incoming payment | Money entered our account (positive amount on the bank payment receipt)     |
| Outgoing payment | Money left our account (minus sign on the bank payment receipt)             |
| Incoming invoice | Invoice issued by another company to us — we paid it                        |
| Outgoing invoice | Invoice we issued to another company — they paid us                         |
| Credit note (Gutschrift) | Credit note issued to us by another company — they paid us                  |
| IG / Reverse charge | Innergemeinschaftliche Leistung: recipient accounts for VAT                 |
| AfA | Absetzung für Abnutzung: depreciable asset                                  |
| Voranmeldefrist | Quarterly VAT advance return deadline                                       |
| Anteil | Proportion of the expense that is business use                              |

---

## Directory model

fibutool separates two concerns: the installed application (shared, persistent) and the working data for a single bookkeeping session (per-session, disposable).

### Application directory

Shared across all sessions. Contains the installed executables and the configuration file. Survives session folder changes and is not touched during a run.

Default: the directory containing `process.py` and `fetcher.py`.  
Override with `--config <path>`.

Contents:
```
process.py       fibutool-process entry point
fetcher.py       fetcher entry point
run.py           fibutool (orchestrator) entry point
config.yaml      shared configuration (API key, rules, defaults)
```

### Work directory (per session)

One folder per bookkeeping run. Contains all input PDFs, intermediate data, and output files for that session. Defaults to the current working directory; override with `--workdir <path>`.

```
<workdir>/
  payments/                    input  — one bank payment receipt PDF per transaction
  invoices/                    input  — one invoice or credit note PDF per invoice document
  payments-ordered/            output — payment receipts renamed with sequential receipt number prefix
  merged/                      output — one merged PDF per payment (invoice document + optional overview + payment receipt)
  match_results.json           output — extraction and match cache (enables resume and journal-only modes)
  journal.csv                  output — bookkeeping journal in CSV format
  <timestamp>_fibutool.log     output — full console transcript for this run
```

Input directories (`payments/`, `invoices/`) are populated by the user before running. All output files are generated by the tool and can be regenerated with `--clean`.

## Configuration (config.yaml)

| Key | Type | Default | Description |
|---|---|---|---|
| `anthropic_api_key` | string | — | Anthropic API key |
| `own_company_names` | list[str] | [] | Our company name(s); used to identify outgoing invoices and detect extraction errors |
| `mixed_vat_label` | string | `"gemischt"` | Label written to the VAT-rate column when an invoice has multiple rates |
| `decimal_separator` | string | `","` | Decimal separator in the CSV output |
| `ig_vat_rate` | int | `20` | Austrian VAT rate (%) applied to the notional IG amount |
| `default_einnahmen_category` | string | `"Waren-/Leistungserlöse"` | Detail category for revenue entries with no category rule match |
| `default_ausgaben_category` | string | `"sonstige Betriebsausgaben"` | Detail category for expense entries with no category rule match |
| `category_rules` | dict[str→str] | {} | Maps counterparty name substrings (case-insensitive) to detail categories |
| `business_percentage_rules` | dict[str→float] | {} | Maps counterparty name substrings to business-use percentage (1–100) |
| `position_business_rules` | dict[str→spec] | {} | Maps counterparty name substrings to position-level business keyword classification |
| `payment_terms_days` | dict[str→int] | {} | Maps counterparty name substrings to maximum days between invoice date and booking date (default: 21); use for suppliers with long payment terms |

All string matches against counterparty names are **case-insensitive substrings**.

`category_rules` values must be one of the allowed `DETAIL_CATEGORIES` (validated on startup).  
`business_percentage_rules` values must be numbers 0 < v ≤ 100 (validated on startup).  
`position_business_rules` values must contain a `business_keywords` list (validated on startup).

## Step 1 — Payment extraction

One API call per payment receipt PDF.

**Extracted fields:**
- `booking_date` — Buchungsdatum, ISO format
- `amount` — always positive decimal
- `currency` — 3-letter code, uppercased
- `counterparty` — the other party: recipient for outgoing, sender for incoming
- `direction` — determined solely from the sign of the amount on the bank payment receipt:
  - minus sign → `"outgoing"` (we paid)
  - no minus sign / positive → `"incoming"` (we received, including refunds)
- `forex_fee` — Fremdwährungsentgelt if shown separately, else 0
- `foreign_amount` — original order amount in the transaction currency (Auftragsbetrag) if the payment was settled in a foreign currency (e.g. USD); null for EUR payments
- `foreign_currency` — 3-letter code for `foreign_amount`; null if `foreign_amount` is null

**Post-extraction rules:**
- R1.1 If direction is not `"outgoing"` and the counterparty contains one of `own_company_names`: confirm direction as `"incoming"`. (A payment can be labelled with our own account name yet still be an incoming credit.)
- R1.2 If direction is `"incoming"` and the counterparty contains one of `own_company_names`: emit a warning — the LLM likely extracted our account name instead of the sender's name.

**Ordering:**
- R1.3 Payments are sorted by booking date, then by filename.
- R1.4 Each payment is assigned a sequential receipt number starting at `last_receipt_number + 1`.
- R1.5 A copy of each payment receipt PDF is written to `payments-ordered/` prefixed with `{receipt_number:03d}_{booking_date}_{original_name}`.

## Step 2a — Invoice extraction

One API call per invoice document PDF.

**Extracted fields:**
- `invoice_date` — ISO format
- `amount` — gross total, always positive
- `currency` — 3-letter code, uppercased
- `invoice_type` — `"incoming_invoice"` | `"outgoing_invoice"` | `"credit_note"`
  - If the issuer is one of `own_company_names`: always `"outgoing_invoice"`
- `counterparty` — the *other* company:
  - incoming invoice / credit note → the issuer (they sent it to us)
  - outgoing invoice → the recipient (we sent it to them)
- `address` — counterparty's street, postal code, town, country (comma-separated; country in German)
- `vat_rate` — dominant VAT percentage printed on the invoice (integer 0–100). Use the rate covering the majority of the amount if mixed.
- `net_total` — total net from the invoice summary if printed separately; else null
- `positions` — all line items (see below)
- `reverse_charge` — `true` only if the invoice explicitly states Reverse Charge / IG Leistung / Steuerschuldumkehr / §13b/§19 UStG / Article 196 / 0% VAT with such a note
- `afa` — `true` if the invoice is for a depreciable tangible asset requiring capitalisation (net > €1000, or not independently usable as GWG); `false` for services, consumables, GWG

**Position extraction:**
- R2.1 Every line item is captured including description, printed amount, and VAT rate.
- R2.2 Austrian "davon X% USt" sub-lines split the parent position into one position per sub-line; each inherits the parent description.

**Position net/gross determination:**
- R2.3 If the sum of extracted amounts ≈ `net_total` (tolerance 0.10): amounts are **net**; gross = net × (1 + rate/100).
- R2.4 Otherwise: amounts are **gross**; net = gross / (1 + rate/100).
- R2.5 Rounding: all derived amounts rounded to 2 decimal places.

**Position validation (warnings):**
- R2.6 If net + vat ≠ gross for any position (tolerance 0.02): warn.
- R2.7 If sum of position grosses ≠ invoice gross total (tolerance 0.05): warn.

**Business classification:**
- R2.8 If `position_business_rules` has a key matching the counterparty: each position is marked `is_business = true` only if its description contains one of the configured `business_keywords`.
- R2.9 Otherwise: all positions are `is_business = true`.

**Category assignment:**
- R2.10 If `category_rules` has a key matching the counterparty: use the mapped category.
- R2.11 Else if `invoice_type == "incoming_invoice"`: use `default_ausgaben_category`.
- R2.12 Else: use `default_einnahmen_category`.

## Step 2b — Matching

One API call for the entire batch (all payments × all invoices).

**Criteria (in order of importance):**
1. **Company name** — use world knowledge to resolve merchant descriptors to legal company names (e.g. "CLAUDE.AI SUBSCRIPTION" → Anthropic). Allow abbreviations, GmbH/Ltd/OG variants, partial matches, minor spelling differences. Name is the primary tiebreaker when multiple invoices otherwise qualify, not a hard gate.
2. **Date** — invoice date should be 0–21 days before booking date; wider gaps occasionally acceptable. Per-counterparty overrides configured in `payment_terms_days` (keyword → max days, substring match) extend the window for suppliers with long payment terms.
3. **Amount** — if the payment has `foreign_amount`/`foreign_currency`, compare those against the invoice amount when the invoice is in that currency; the EUR amount cannot be compared to a foreign-currency invoice. Otherwise the payment amount and invoice amount must differ by < 1 EUR. A EUR amount difference > 1 EUR is a hard disqualifier regardless of other signals. Note any currency difference in the reason.
4. **Direction** — strict:
   - outgoing payment → match `incoming_invoice` only
   - incoming payment → match `outgoing_invoice` or `credit_note` only

When amount difference < 0.01 (in the relevant currency), date is within range, and direction matches, and only one invoice candidate satisfies all three — match regardless of name similarity and note the name discrepancy in the reason.

**Assignment rules:**
- R3.1 Each invoice is assigned to at most one payment.
- R3.2 Each payment is assigned to at most one invoice.
- R3.3 If no plausible match exists, `invoice_index` is null.
- R3.4 If the LLM assigns the same invoice to multiple payments, only the first assignment is kept; subsequent ones are rejected with a warning.
- R3.5 If the LLM returns no assignment for a payment, a warning is emitted.
- R3.6 Reasons in the LLM response must reference filenames, not array indices.

**Business percentage:**
- R3.7 After matching, `business_percentage_rules` is applied to the matched invoice's counterparty.
- R3.8 Default business percentage: 100%.

---

## Step 3 — PDF merging

One merged PDF per payment, written to `merged/` with the same name as the ordered payment receipt file.

**Page order:**
1. Invoice document pages (all pages of the invoice document PDF)
2. Overview page (only if any position has `is_business = false`) — see R5
3. Payment receipt pages (all pages of the ordered payment receipt PDF)

Unmatched payments produce a merged PDF with payment receipt pages only (no invoice document, no overview).

## Step 4 — Journal CSV generation

One row per payment. Encoding: UTF-8 with BOM. Delimiter: semicolon.

### Column layout

| # | Name | Content |
|---|---|---|
| 1 | Year | Booking date year |
| 2 | Receipt | Receipt number, zero-padded to 3 digits |
| 3 | Category | `Einnahmen` or `Ausgaben` |
| 4 | Detail category | See R4.2–R4.3 |
| 5 | Date | Booking date DD.MM.YYYY |
| 6 | Counterparty | Name and address comma-separated |
| 7 | (empty) | |
| 8 | Weiterverkauf | (empty, unused) |
| 9 | AfA | `WAHR` if invoice.afa, else `FALSCH` |
| 10 | Gross (incl. VAT) | |
| 11 | Gross (anteilig) | |
| 12 | Anteil | Business-use percentage |
| 13 | VAT rate | `{rate}%`, `gemischt`, or `20%` as fallback |
| 14 | VAT amount | |
| 15 | VAT amount (anteilig) | |
| 16 | Net | |
| 17 | Net (anteilig) | |
| 18 | VAT deadline | Quarterly Voranmeldefrist DD.MM.YYYY |
| 19 | IG | IG VAT rate if reverse charge, else empty |
| 20 | ESt abzugsfähig | (empty, unused) |
| 21 | IG VAT (anteilig) | IG notional VAT if reverse charge, else empty |
| 22 | Invoice file | Original invoice PDF filename; empty if unmatched |
| 23 | Payment file | Original payment receipt PDF filename |

### Category rules

- **R4.1** A payment is **Einnahmen** if and only if: direction = `"incoming"` AND invoice is matched AND `invoice_type ∈ {"outgoing_invoice", "credit_note"}`.
- **R4.2** All other payments are **Ausgaben** — including outgoing payments and incoming payments without a matching revenue-type invoice (refunds).

### Counterparty

- **R4.3** Einnahmen: counterparty name and address from the invoice (= our customer).
- **R4.4** Ausgaben: counterparty name and address from the invoice if matched, else from the payment.

### Amount base (gross)

- **R4.5** If any invoice position has `is_business = false`: gross = sum of gross amounts of business-only positions.
- **R4.6** Otherwise: gross = full payment amount.
- **R4.7** When invoice and payment currencies differ (foreign-currency invoice), position amounts are in the invoice currency and cannot be used for EUR journal fields; treat as R4.6 even if positions exist.

### Effective base

- **R4.8** `effective_base = gross − forex_fee`. The forex fee is excluded from the VAT base but is itself a deductible business expense included in gross.

### VAT

- **R4.9** If active positions available: VAT = sum of position VAT amounts.
  - Single rate: write `{rate}%`.
  - Multiple rates: write `mixed_vat_label` (default `"gemischt"`); IG is suppressed.
- **R4.10** Else if invoice has a `vat_rate`: VAT = `effective_base × rate / (100 + rate)`.
- **R4.11** Else (no invoice or no vat_rate): VAT = `effective_base × 20 / 120`.

### IG (Reverse charge / innergemeinschaftlicher Erwerb)

- **R4.12** IG applies only when `invoice.reverse_charge = true` and the VAT rate is single (not mixed).
- **R4.13** IG column value: `ig_vat_rate` (default 20).
- **R4.14** IG VAT amount (anteilig) = `ig_vat_rate / 100 × gross_anteilig`.

### Anteil (business-use proportion)

- **R4.15** `anteilig` fields = full field × `business_percentage / 100`.

### Refund sign

- **R4.16** When category = `Ausgaben` and direction = `"incoming"` (refund): all monetary amounts (gross, gross\_anteilig, VAT, VAT\_anteilig, net, net\_anteilig, IG VAT\_anteilig) are negated, so the entry reduces the expense total.

### VAT deadline

- **R4.17** Deadline is the quarterly Voranmeldefrist for the **payment booking date** (Ist-Besteuerung):
  - Q1 (Jan–Mar) → 15 May
  - Q2 (Apr–Jun) → 15 Aug
  - Q3 (Jul–Sep) → 15 Nov
  - Q4 (Oct–Dec) → 15 Feb of the following year

## R5 — Overview page (mixed business/private positions)

When an invoice document has at least one private (`is_business = false`) position, a one-page PDF summary is inserted between the invoice document and the payment receipt in the merged PDF. It lists every position with its net, VAT, gross, and classification (abzugsfähig / privat), plus a total for business-only positions.

## Operation modes

| Mode | Trigger | Behaviour |
|---|---|---|
| **Full** | No `match_results.json` exists (or `--clean`) | Extract all payments and invoices, match, merge, write journal |
| **Resume** | `match_results.json` exists and `--clean` is not set | Load previous results; extract only new invoices; re-match previously unmatched payments; skip already-matched payments |
| **Journal-only** | `--journal-only` flag | Load `match_results.json`; skip extraction, matching, and merging; regenerate `journal.csv` only |

**Resume behaviour:**
- R6.1 Previously matched payments are not re-processed.
- R6.2 Previously unmatched payments are re-matched against all available invoices (old + new), excluding already-matched invoices.
- R6.3 Previously extracted payments are not re-extracted.

**Flags:**
- `--last-receipt-number N` / `-n N`: required in full mode; first receipt number = N + 1.
- `--clean`: remove all output files before running.
- `--only-payment FILE`: process a single payment receipt PDF instead of all files in `payments/`.
- `--only-invoice FILE`: process a single invoice document PDF instead of all files in `invoices/`.

## Error handling and warnings

- All console output is mirrored to a timestamped log file in the work directory.
- If the LLM returns non-JSON or unparseable content, the raw response is saved to a timestamped debug file and the affected payment receipt or invoice document PDF is skipped with a warning.
- Warnings are collected throughout the run and printed as a summary at the end, prefixed with `[module_name]` and the triggering filename.
- If a payment receipt PDF fails extraction it is skipped; if all payment receipts fail the tool exits.
- Invoice document extraction failures are recorded as warnings and the invoice document is omitted from matching.
- Rate limit errors from the API trigger automatic retries with increasing delays (60 s, 180 s, 300 s, 600 s), then one final attempt.

## Known gaps and inconsistencies

**G1 — IG suppressed for mixed-VAT reverse-charge invoices**
When active positions contain more than one VAT rate, the IG column is forced empty even when `invoice.reverse_charge = true`. A reverse-charge invoice with mixed rates produces no IG reporting.

**G2 — Foreign-currency invoice with partial business use produces wrong amounts**
If `position_business_rules` classify some positions as private and the invoice currency differs from the payment currency, `gross` is computed from business-position amounts in the invoice currency (e.g. USD), not in EUR. The resulting journal row contains incorrect EUR values. The currency guard only protects the all-business-positions path.

**G3 — `invoice.matched` is written but never read**
`matcher.py` sets `invoice.matched = True` and it is persisted in the cache, but nothing in the pipeline reads the field. Either dead code or a placeholder for a future feature.
